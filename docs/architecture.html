总览

DeepSeek Harness（dsh）是一个由 DeepSeek AI 开发的开源 AI Agent 框架。核心设计原则：一切皆插件——从模型适配器到 Agent 循环本身，每个组件都可通过配置替换。底层由 Cordis 框架驱动。

关键区分

传统框架：核心代码 → 调用 → 插件（插件是被动被调用方）
dsh 框架：插件 → 注册到 → ctx（插件是主动贡献方，消费方从 ctx 获取能力）
没有调用者，只有参与者。没有特权核心需要 patch。

传统方式的痛点

在理解 dsh 的架构之前，先看清楚它要替代的"传统方式"有什么问题。以下痛点不是假设——它们是构建 AI Agent 框架时几乎必然遇到的。

痛点 1：硬编码架构——核心不可替换

传统框架有一个"核心"（core），核心代码调用插件。核心决定了模型怎么请求、工具怎么执行、会话怎么存储。想替换其中任何一个，要么 fork 整个核心，要么等核心作者加一个 hook。

传统方式

核心代码

模型请求逻辑写死在核心 → 想换 LLM？改核心代码
工具执行流水线写死在核心 → 想加审批？改核心代码
会话存储格式写死在核心 → 想换 SQLite 为 Postgres？改核心代码

核心是黑盒，扩展靠 fork 或 PR，不是靠配置。

dsh 方式

没有核心

ctx.llm 是一个 seam → 换 LLM = 注册新 provider
ctx.tools 是一个 seam → 加审批 = 监听 tools/pre-execute
ctx.sessions 是一个 seam → 换存储 = 注册新 persistence backend

Agent 循环本身（ctx.agentLoop）都是可替换的配置行。

痛点 2：紧耦合——插件之间直接 import

传统框架的插件通过直接导入彼此的代码来协作。工具插件 import 模型适配器，UI 插件 import 会话存储。结果是：换任何一个组件，依赖它的所有插件都要改代码。

// 传统方式：直接 import → 紧耦合
import { DeepSeekAdapter } from '@core/llm'       // 工具直接依赖具体 LLM 实现
import { SessionStore } from '@core/session'     // UI 直接依赖具体存储实现
import { ToolRegistry } from '@core/tools'       // 循环直接依赖工具注册表

// 想把 DeepSeekAdapter 换成 MyAdapter？
// → 改这个文件的 import
// → 改所有其他 import 了 DeepSeekAdapter 的文件
// → 祈祷没有循环依赖
// → 祈祷类型兼容
// → 上线后发现有 10 个地方偷偷依赖了 DeepSeekAdapter 的私有方法
紧耦合的连锁反应

直接 import 导致替换成本随依赖数量线性增长。一个组件被 20 个插件 import，替换它就要改 20 个文件。实际项目中，这通常意味着"不换"——技术债由此积累。

痛点 3：生命周期地狱——手动 cleanup

传统框架中，插件注册的事件监听器、定时器、连接池需要手动清理。忘了清理 → 内存泄漏、僵尸监听器、错误在已卸载的插件上触发。

// 传统方式：手动管理生命周期
class MyPlugin {
  mount() {
    this.listener = onModelRequest(this.handle)
    this.timer = setInterval(this.tick, 1000)
    this.conn = createConnection(dbUrl)
  }

  unmount() {
    // 忘了移除 listener? → 僵尸监听器，模型请求时触发已卸载的 handler
    offModelRequest(this.listener)
    // 忘了 clearInterval? → 定时器永远跑，内存泄漏
    clearInterval(this.timer)
    // 忘了关闭连接? → 连接池耗尽
    this.conn.close()
    // 如果有 10 个资源要清理呢? 20 个呢?
    // 如果 async cleanup 有顺序依赖呢?
    // 如果热更新时旧实例没清理干净就加载新实例呢?
  }
}
热更新 = 灾难

传统框架几乎不支持热更新——因为旧实例的资源没有自动清理机制。热更新意味着卸载旧插件、加载新插件，但如果旧插件忘了清理一个定时器，它会在新插件运行时继续触发，导致不可预测的状态污染。大多数框架选择不支持热更新来回避这个问题。

痛点 4：部署与定制——一份代码一种部署

传统框架的部署形态是固定的。想给不同用户不同的能力集？想在某些部署中关闭某些工具？想在远程沙箱中运行而不是本地？通常需要 fork 代码或维护多个分支。

传统方式：fork 定制

企业版要关闭 Bash 工具 → fork 代码，注释掉
云端版要用远程沙箱 → fork 代码，改执行逻辑
定制版要换模型 → fork 代码，改模型调用
每个定制一个分支，合并时地狱。

dsh 方式：配置定制

企业版关闭 Bash → disabled: true
云端版用远程沙箱 → 注册新 ctx.fs + ctx.subprocess
定制版换模型 → llm.adapter: ./my-adapter
一份代码，无限部署形态，靠配置区分。

dsh 解决了什么

上一节列出了痛点。这一节说明 dsh 的每个设计决策如何精确对应这些痛点，以及它们带来的长远好处。

解决方案 1：ctx 中枢 → 消除紧耦合

插件不 import 彼此，而是通过 ctx 上的命名服务交互。工具插件不 import LLM 适配器，而是 ctx.llm.stream()。UI 不 import 会话存储，而是 ctx.sessions.append()。

// dsh 方式：通过 ctx 交互，零直接依赖
export const inject = ['llm', 'sessions']

export function apply(ctx: Context) {
  // ctx.llm 是接口，不关心是 DeepSeek 还是自定义适配器
  const stream = ctx.llm.stream(request)
  // ctx.sessions 是接口，不关心是 JSONL 还是 SQLite
  ctx.sessions.append(sessionId, event)
}
长远好处

替换成本从 O(N) 降到 O(1)。换一个组件只需注册新 provider，所有消费方零修改。这意味着技术债不再随时间积累——组件可以随时升级，不需要"等到下个大版本一起改"。

解决方案 2：可逆注册 → 消除生命周期地狱

所有注册（ctx.on()、ctx.plugin()、ctx.tools.register()）都是副作用。Cordis 跟踪每个插件注册的所有副作用，卸载时自动 unwind。开发者只管注册，不管清理。

// dsh 方式：注册即可，不用 cleanup
export function apply(ctx: Context) {
  ctx.on('agent/pre-step', handler)    // 自动解绑
  ctx.tools.register(myTool)            // 自动注销
  ctx.effect(() => {
    const timer = setInterval(tick, 1000)
    return () => clearInterval(timer)  // 自动调用
  })
  // 没有 unmount() 方法 — 不需要
}
长远好处

热更新成为一等公民。因为副作用自动清理，HMR 可以安全地卸载旧实例、加载新实例。开发者编辑代码保存，旧插件的所有资源自动释放，新插件干净加载。这在传统框架中几乎不可能实现。

解决方案 3：inject 依赖 → 消除加载顺序问题

插件声明 inject = ['llm', 'tools']，框架自动等待依赖就绪后再调用 apply。配置文件中的位置无关紧要。依赖消失时自动卸载，恢复时自动重载。

长远好处

配置替换可以在运行时进行。卸载 dsh-bash-local 条目，挂载另一个 shell provider，所有依赖 shell 的插件自动重启到新实现。不需要重启服务，不需要改代码。

解决方案 4：层叠配置 → 消除部署碎片化

一份代码通过 Profile + Bundle + Patch 产生无限部署形态。企业版、云端版、定制版共享同一套代码，靠配置区分。

# 企业版 cordis.patch.yml — 关闭危险工具
- id: bash
  disabled: true

# 云端版 cordis.patch.yml — 使用远程沙箱
- id: remote-sandbox
  name: './remote-sandbox.ts'

# 定制版 cordis.patch.yml — 换模型
llm:
  adapter: "./custom-llm-adapter"

# 同一份代码，三种部署，零 fork
长远好处

维护成本从 O(部署形态数) 降到 O(1)。不再为每个客户维护一个分支。所有部署共享同一套代码和测试，配置差异在配置文件中表达，不在代码中。

解决方案 5：事件作为唯一扩展点 → 消除扩展点不明确

传统框架的 hook 函数散落在代码各处，没有统一约定。dsh 用三类事件覆盖所有扩展场景，每个事件有明确的触发时机、分发模式和类型签名。

一句话总结

传统框架的扩展成本随依赖深度线性增长，dsh 的扩展成本恒定为 O(1)——因为所有交互通过 ctx 中转，所有注册自动撤销，所有配置可被覆盖。这不是一个功能，是一个架构范式。

插件模型：ctx 中枢

上一节从宏观对比了传统框架与 dsh 的差异。从本节开始，深入 dsh 的架构细节——先看插件如何通过 ctx 交互，再看插件如何注册和加载，最后看运行时的完整生命周期。

所有插件通过 Cordis 的 Context（简称 ctx）交互。插件向 ctx 注册服务、事件监听器和工具；消费方从 ctx 获取这些能力。插件之间从不直接 import。

图 1. ctx 中枢模型 — 左侧插件向 ctx 注册能力（绿色虚线），右侧消费方从 ctx 获取能力（蓝色实线）。插件之间无直接 import。

分层组合

dsh 的配置不是单一文件，而是多层叠加。每一层可以覆盖下层的任意配置行。

图 2. 配置层叠顺序 — 上层覆盖下层。每层可 patch 任意配置行（替换或插入）。最终生成的配置树决定加载哪些插件、使用什么参数。

配置覆盖机制

系统的每项配置是一个带 ID 的"行"（row）。上层配置通过 patch 替换或插入行。这意味着任何组件都可被精确替换：

# 查看实际加载的完整配置树
dsh --profile web --dump-config

# 输出示例（每行都是一个可被 patch 的配置项）
llm.adapter        = "@deepseek-ai/dsh-llm-deepseek"
llm.model          = "deepseek-chat"
tools.registry      = ["@deepseek-ai/dsh-tool-bash", ...]
agentLoop.driver    = "@deepseek-ai/dsh-agent-loop"
fs.provider         = "local"
sandbox.backend    = "landlock"

# ~/.dsh/cordis.patch.yml — 替换 LLM 后端
llm:
  adapter: "./my-custom-adapter"
  model: "my-model-v2"
  api_key: "$MY_API_KEY"
关键点

agentLoop 本身也是一个配置行。你可以注册一个全新的 ctx.agentLoop 实现来替换整个 Agent 循环逻辑——这不是 hack，是设计意图。

插件注册机制

上一节讲了"为什么"一切皆插件。这一节讲"怎么"——插件从代码到运行的全过程：如何声明、如何被发现、如何加载、如何注册能力、如何被依赖、如何被卸载。

三种插件形态

Cordis 接受三种插件写法，底层机制相同：

// 1. 函数插件 — 最常见
export function apply(ctx: Context) {
  ctx.on('agent/pre-step', handler)
}

// 2. 对象插件 — 带名称和 apply 方法
export const objectPlugin = {
  name: 'my-plugin',
  apply(ctx: Context) { /* ... */ }
}

// 3. 类插件 — 继承 Service，同时注册一个服务
export class MyService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'myService')  // 注册到 ctx.myService
  }
  doWork() { return 'done' }
}
选择原则

用函数插件直到你需要暴露一个服务——此时改用类插件（继承 Service）。对象插件用于需要显式 name 的场景。

cordis.yml：组合文件

插件不通过 import 挂载，而是通过 cordis.yml 声明式组合。cordis.yml 是一个插件条目列表，每个条目描述一个要加载的插件：

# cordis.yml — 应用组合文件
- id: llm                          # 稳定标识，用于 HMR diff
  name: '@deepseek-ai/dsh-llm-deepseek'  # 模块路径或 npm 包名
  config:                           # 传给插件 apply 的配置
    model: deepseek-chat
    api_key: $DEEPSEEK_API_KEY

- id: tools
  name: '@deepseek-ai/dsh-tools'

- id: my-tool
  name: './my-tool.ts'               # 相对路径也行

- id: debug-plugin
  name: './debug.ts'
  disabled: true                     # 保留条目但不加载

- id: isolated-shell
  name: '@deepseek-ai/dsh-shell-local'
  isolate: true                     # 独立服务实例，不共享
字段作用必需
name模块路径或 npm 包名——Loader 用它 resolve 插件代码是
id条目的稳定标识。HMR 用它 diff 配置变更：无 id 的条目每次读配置都被视为删除+新增强烈建议
config传给 apply(ctx, config) 的配置对象否
disabledtrue 时不加载，但保留条目。翻回 false 即恢复否
isolate给该条目独立的服务实例，不与其他条目共享同一 ctx key否
常见陷阱

条目在 cordis.yml 中的位置不决定加载顺序。加载顺序由 inject 依赖决定——所有条目并发启动，依赖满足后才进入 ACTIVE。如果插件"什么都不做"，检查它的 inject 是否有未被满足的服务。

依赖注入与加载顺序

插件通过 inject 数组声明它需要哪些服务。Cordis 持有插件在 PENDING 状态直到所有依赖就绪。cordis.yml 中的位置不决定加载顺序——依赖关系决定。

// consumer.ts — 声明依赖 'greeter' 和 'tools'
export const name = 'consumer'
export const inject = ['greeter', 'tools']

export function apply(ctx: Context) {
  // 进入 apply 时，ctx.greeter 和 ctx.tools 保证已就绪
  const result = ctx.greeter.greet('world')
  ctx.tools.register(myTool)
}
# cordis.yml — 顺序无所谓
- name: './consumer.ts'      # 先列出来也没问题
- name: './greeter.ts'      # 后列出来也行

# consumer 的 inject=['greeter'] 让它等 greeter ACTIVE 后才加载
# 交换两行顺序，输出完全一样
依赖是动态跟踪的

inject 不是一次性启动检查。如果运行时某个被依赖的服务消失（provider 被卸载或热替换），所有依赖它的插件自动卸载，当服务恢复时重新加载。这就是配置替换能工作的原因：卸载 dsh-bash-local 条目，挂载另一个 shell provider，所有 inject: ['shell'] 的插件干净地重启到新实现。

// 可选依赖 — 不用 inject，运行时探测
export function apply(ctx: Context) {
  const greeter = ctx.get('greeter')  // 无 provider 时返回 undefined
  console.log(greeter?.greet('maybe') ?? 'no greeter')
}

服务注册：Service 类 + 声明合并

暴露服务需要两步：运行时注册（让 ctx.xxx 可用）和编译时类型声明（让 TypeScript 认识 ctx.xxx）。

// greeter.ts — 注册一个服务
import { Service, type Context } from '@deepseek-ai/cordis'

Fiber 状态机

每个加载的插件实例拥有一个 Fiber——运行时句柄，经历以下状态：

图 4. Fiber 状态机 — PENDING（等依赖）→ LOADING（apply 中）→ ACTIVE → UNLOADING（清理）→ DISPOSED。apply 抛异常进入 FAILED。
诊断"什么都不做"的插件

插件 inject 了一个没人提供的服务 → 永远停在 PENDING，不报错、不输出。诊断方法：遍历 ctx.registry 检查 Fiber 状态。PENDING 是合法状态——provider 可能稍后才挂载。

// 诊断脚本：检查哪些插件卡在 PENDING
import { FiberState, type Context } from '@deepseek-ai/cordis'

export function apply(ctx: Context) {
  setTimeout(() => {
    for (const runtime of ctx.registry.values()) {
      for (const fiber of runtime.fibers) {
        if (fiber.state === FiberState.PENDING)
          console.log(`${fiber.name} PENDING — 依赖未满足`)
      }
    }
  }, 500)
}

副作用与自动撤销

所有通过 Cordis API 注册的内容都是副作用——插件卸载时自动撤销，无需手动 cleanup。这是热插拔的基础。

注册 API注册内容卸载时自动撤销
ctx.on(event, listener)事件监听器移除监听器
ctx.plugin(child)子插件递归 dispose 子插件
super(ctx, 'name')服务（Service 类）从 ctx 移除服务
ctx.tools.register(...)工具注册注销工具
ctx.effect(() => disposer)自定义资源（定时器、连接等）调用 disposer
 
// 所有注册都是副作用 — 卸载时自动 unwind
export function apply(ctx: Context) {
  ctx.on('agent/pre-step', handler)       // → unload 时解绑
  ctx.plugin(GreeterService)               // → unload 时移除服务
  ctx.tools.register(myTool)                 // → unload 时注销工具

  // 非 Cordis 管理的资源 → 用 ctx.effect() 包装
  ctx.effect(() => {
    const timer = setInterval(tick, 1000)
    return () => clearInterval(timer)  // disposer
  })
}
ctx.effect() 的用途

大多数情况不需要手写 ctx.effect()——内置 API（on、plugin、register）已经是副作用。只在管理 Cordis 不认识的资源（定时器、网络连接、文件 watcher）时才需要。disposer 在卸载时执行，async disposer 并发执行（按注册的逆序开始）。

热更新（HMR）

因为卸载释放副作用、加载跟随依赖，HMR 可以通过卸载+重载替换运行中的插件。编辑 cordis.yml 本身也会被感知——Loader 按 id diff 条目，只挂载/卸载/重配置变更的部分。

# cordis.yml — 启用 HMR
- id: hmr
  name: '@deepseek-ai/cordis-plugin-hmr'
  config:
    root: ['.']

# 编辑 hello.ts 并保存 →
# 1. 旧实例卸载（所有副作用 unwind）
# 2. 新代码加载
# 3. apply 重新执行
# 4. 依赖此服务的插件自动重启
为什么条目需要 id

没有 id 的条目每次读配置都生成新 id，所以任何 cordis.yml 编辑都被视为"删除+新增"，即使该条目自身没改也会重新挂载。给条目加 id 让 Loader 正确 diff。

事件系统

运行时生命周期中的 agent/pre-step、tools/execute 等节点就是事件。事件是 dsh 的唯一扩展点——插件不通过继承或 hook 函数扩展系统，而是通过监听事件。三类事件覆盖所有扩展场景。

三种事件域

事件域代表事件持久性用途
Session turn/*, step/*, user/message, assistant/*, tool/* 持久（追加到日志） 必须在重载后存活的事实。Fork/Resume/Replay 全部从此派生。
Agent agent/pre-step, agent/request, agent/turn-stopping 实时（不持久） 观察/拦截进行中的工作。携带活跃 Agent 句柄。
Capability fs/*, tools/*, telemetry/* 实时（不持久） 附加策略和适配器到 seam，不导入循环本身。

agent/request

tools/execute

// Waterfall 拦截示例：在模型请求前注入系统上下文
ctx.on('agent/pre-step', (event, next) => {
  if (event.messages.length === 0) {
    return 'reject'          // 拒绝 → 关闭 turn
  }
  const rewritten = injectContext(event.messages)
  return next({ ...event, messages: rewritten })  // 重写后委托
})

// Serial 观察示例：轮次结束时记录遥测
ctx.on('agent/turn-stopping', (event) => {
  ctx.telemetry.record({
    type: 'turn_end',
    steps: event.stepCount,
    tokens: event.tokenUsage
  })
  // 无 next() — 不能阻止轮次结束
})

标红 = 通过 ctx 可替换的核心组件
Part 2 · 需求面板三层架构

基于第一部分 dsh 框架。核心思想：需求面板不是硬编码业务逻辑，而是事件驱动的状态机——每一层流转由事件触发，任务队列派发器通过监听事件串行派发，任何一层都可被替换或扩展。

三层流水线模型

需求面板是一个三阶段流水线。需求从需求层提出，自动丢入任务队列按序执行，到验收层逐项检验。验收不通过则返工重新入队，全部通过则进入验收完成队列。每个需求在整个生命周期中保留完整上下文。用户提需求的方式不变——照常提出，提交后自动排队，无需人工触发。

需求层：提出需求 + 思考构成要素 + 生成验收要素

需求层负责定义"做什么"和"怎么算做完"。用户或 Agent 提出需求后，系统自动思考需求的构成要素，并生成对应的验收要素。

需求构成要素（自动拆解）

标题 — 一句话描述需求
详细描述 — 背景、目标、约束
优先级 — critical / high / medium / low
范围 — 涉及的模块/文件
依赖 — 前置需求 ID
上下文锚点 — 相关会话片段、代码位置

验收要素（定义"做完"）

功能验收 — 核心功能是否实现
测试验收 — 单元/集成测试是否通过
代码验收 — 是否符合代码规范
文档验收 — 是否更新相关文档
性能验收 — 是否满足性能要求
用户确认 — 用户是否签字认可

需求层产出

需求层完成后，产出一个包含需求构成要素和验收要素的结构化需求，状态为 queued，随即丢入任务队列排队执行。

执行层：任务队列按序执行

需求提交后直接进入任务队列，队列 worker 按提交顺序串行消费——一次只执行一个，无需人工触发。用户提需求的方式完全不变：照常用 propose_requirement 工具，提交后自动排队。执行时每步动作都记录到执行上下文中。

任务队列机制

需求提交时 emit requirement/queued → 队列 worker 监听此事件 → enqueue 入队 → 串行派发给执行 agent（驱动完整 turn 执行）→ 收尾（accepted / rework）后再取下一个。队列空则空闲，来活即动。

验收层：对照验收要素逐项检查

执行完成后需求进入验收层。Agent 先自检（对照验收要素逐项验证），然后提交用户确认。全部通过进入验收完成队列；任一不通过进入返工。

验收层产出

验收层对每个验收要素给出通过/失败判定。全部通过 → accepted（验收完成队列）。任一失败 → rework（返工记录），回到需求列表重新执行。

返工循环

验收不通过时，系统创建返工记录（包含失败原因、涉及的验收项、建议修复方案），需求状态回退到 queued，重新入队排队。轮到它时，Agent 看到返工记录后针对性修复，而非从头开始。

返工 ≠ 从头开始

返工时 Agent 能看到所有历史上下文：上轮执行做了什么、验收哪项失败、失败原因是什么。Agent 只需针对失败项修复，不必重做已通过的部分。

上下文保留

每个需求在整个生命周期中保留完整上下文链，Agent 在任何阶段都能看到完整历史。

阶段保留的上下文
需求层原始需求描述、拆解后的构成要素、验收要素、创建者、创建时间
执行层每步执行动作（代码变更、工具调用、模型请求）、执行日志、中间产物
验收层每项验收结果（通过/失败）、失败原因、Agent 自检报告、用户确认记录
返工返工次数、每次返工原因、修复方案、修复后的重新验收结果
完成完整生命周期摘要、总耗时、返工次数、最终交付物引用

export type RequirementId = Brand<string, 'RequirementId'>

// ── 需求生命周期阶段 ──
export type RequirementStage =
  | 'backlog'      // 需求队列：待评审，不自动执行（实际新增）
  | 'queued'       // 执行队列：已丢入，等待 FIFO 派发
  | 'executing'     // 执行层：子 agent 新会话执行中（同一时刻仅 1 个）
  | 'accepting'     // 待验收池：执行完进入，可堆积多个
  | 'rework'        // 返工：自动重入执行队列（MAX_REWORK 上限）
  | 'accepted'      // 完成：进入验收完成队列

// ── 需求主体 ──
export interface Requirement {
  id: RequirementId
  title: string
  description: string
  priority: 'critical' | 'high' | 'medium' | 'low'
  stage: RequirementStage

declare module '@deepseek-ai/cordis' {
  interface Context {
    requirements: RequirementsService
    requirementsStore: RequirementsStore   // 存储 seam（可替换）
  }
  interface Events {
    'requirement/created'(req: Requirement): void
    'requirement/queued'(id: RequirementId): void      // 已提交，进入任务队列
    'requirement/enqueued'(id: RequirementId): void    // 队列 worker 已入队
    'requirement/executing'(id: RequirementId, round: number): void
    'requirement/accepting'(id: RequirementId): void
    'requirement/accepted'(id: RequirementId): void
    'requirement/rework'(id: RequirementId, reason: string): void
  }
}

// ── 存储 Seam：接口契约（Definition）──
// Provider 可实现 JSONL / SQLite / 远程后端，替换时消费方零修改
export interface RequirementsStore {
  save(req: Requirement): Promise<void>
  get(id: RequirementId): Promise<Requirement>
  update(id: RequirementId, patch: Partial<Requirement>): Promise<void>
  list(filter: { stage?: RequirementStage }): Promise<Requirement[]>

  // ── 任务队列（FIFO，持久化，Fork/Resume 保留） ──
  enqueue(id: RequirementId): Promise<void>          // 追加到队尾
  dequeue(): Promise<RequirementId | null>      // 取队首（空则 null）
  peek(): Promise<RequirementId | null>        // 看队首（不出队）
}

// ── 服务：业务逻辑（Consumer），持久化全部委托给注入的 Store ──
export class RequirementsService extends Service {
  constructor(ctx: Context) { super(ctx, 'requirements') }

  private get store(): RequirementsStore { return this.ctx.requirementsStore }

  // ── 需求层 ──
  async create(input: RequirementInput): Promise<Requirement> {
    // 自动拆解需求构成要素 + 生成验收要素
    const elements = await this.decomposeElements(input)
    const acceptanceCriteria = await this.generateAcceptanceCriteria(input, elements)
    const req = { ...input, elements, acceptanceCriteria, stage: 'drafting' }
    await this.store.save(req)
    this.ctx.emit('requirement/created', req)
    return req
  }

  async submit(id: RequirementId): Promise<void> {
    await this.store.update(id, { stage: 'queued' })
    this.ctx.emit('requirement/queued', id)       // → 队列 worker 入队派发
  }

  // ── 执行层 ──
  async startExecution(id: RequirementId): Promise<void> {
    const req = await this.store.get(id)
    const round = req.reworkCount + 1
    req.executions.push({ round, startedAt: Date.now(), actions: [], isRework: round > 1 })
    req.stage = 'executing'
    await this.store.save(req)
    this.ctx.emit('requirement/executing', id, round)
  }

  async recordAction(id: RequirementId, action: ExecutionAction): Promise<void> {
    const req = await this.store.get(id)
    const exec = req.executions[req.executions.length - 1]
    exec.actions.push(action)                    // 保留执行上下文
    await this.store.save(req)
  }

  async completeExecution(id: RequirementId, summary: string): Promise<void> {
    const req = await this.store.get(id)
    const exec = req.executions[req.executions.length - 1]
    exec.completedAt = Date.now()
    exec.summary = summary
    req.stage = 'accepting'
    await this.store.save(req)
    this.ctx.emit('requirement/accepting', id)  // → 触发验收层
  }

  // ── 验收层 ──
  async submitAcceptance(id: RequirementId, record: AcceptanceRecord): Promise<void> {
    const req = await this.store.get(id)
    req.acceptances.push(record)

    if (record.overall === 'passed') {
      req.stage = 'accepted'
      await this.store.save(req)
      this.ctx.emit('requirement/accepted', id)   // → 进入验收完成队列
    } else {
      req.reworkCount++
      req.stage = 'rework'
      await this.store.save(req)
      this.ctx.emit('requirement/rework', id, record.reworkSuggestion ?? '')
      // → 队列 worker 监听 rework 事件 → 重新入队（回队尾）
    }
  }

  // ── 查询 ──
  async get(id: RequirementId): Promise<Requirement> { return this.store.get(id) }
  async update(id: RequirementId, patch: Partial<Requirement>): Promise<void> { return this.store.update(id, patch) }
  async list(filter: { stage?: RequirementStage }): Promise<Requirement[]> { return this.store.list(filter) }

  // ── 任务队列原语（透传 store） ──
  async enqueue(id: RequirementId): Promise<void> { return this.store.enqueue(id) }
  async dequeue(): Promise<RequirementId | null> { return this.store.dequeue() }
  async peek(): Promise<RequirementId | null> { return this.store.peek() }
  async getFullContext(id: RequirementId): Promise<RequirementContext> {
    // 返回完整生命周期上下文（需求要素 + 所有执行 + 所有验收 + 返工历史）
  }
}

任务队列派发器

dsh-requirements-queue 是任务队列的"胶水"插件。蓝图里它监听 queued 事件自动入队派发；实际实现拆为需求队列(backlog) + 执行队列(execQueue)双层，并把执行与验收解耦，详见 Part 3。下面是蓝图版单队列实现。

export const inject = ['requirements', 'agents']

export function apply(ctx: Context) {
  let busy = false        // 是否已有需求在执行（串行）

  // ── 需求提交 → 入队 ──
  // 用户提需求方式不变：propose_requirement → submit → queued
  ctx.on('requirement/queued', (id) => {
    ctx.requirements.enqueue(id)      // 追加到队尾
    ctx.emit('requirement/enqueued', id)
    pump()                             // 尝试派发
  })

  // ── 队列串行派发：一次只执行一个 ──
  async function pump() {
    if (busy) return                      // 有需求在跑 → 等它收尾
    const id = await ctx.requirements.dequeue()  // 取队首
    if (!id) return                       // 队列空 → 空闲

    busy = true
    await ctx.requirements.startExecution(id)   // → executing

    // 驱动 agent 完整执行一个 turn（后台，无需人工触发）
    // 语义 = 向 agent 输入队列提交一条消息，让它认领并开始新 turn
    const req = await ctx.requirements.get(id)
    await ctx.agents.submit(
      `请执行需求 #${id}「${req.title}」：\n` +
      `先 list_requirements 查看构成要素与验收要素，逐个完成，\n` +
      `每步 recordAction 记录执行上下文，\n` +
      `完成后 complete_execution 提交验收`
    )
  }

  // ── 收尾释放队列，派发下一个 ──
  // 验收通过 → 直接派发下一个
  ctx.on('requirement/accepted', () => { busy = false; pump() })
  // 验收失败 → 返工重新入队（回队尾），再派发下一个
  ctx.on('requirement/rework', async (id) => {
    await ctx.requirements.enqueue(id)
    busy = false
    pump()
  })
}

ctx.tools.register(defineTool({
  name: 'submit_acceptance',
  description: '提交需求验收结果。逐项检查验收要素，全部通过则进入验收完成队列，任一失败则重新入队。',
  parameters: {
    requirementId: { type: 'string', required: true },
    results: {
      type: 'array', required: true,
      items: {
        type: 'object',
        properties: {
          itemId: { type: 'string' },
          passed: { type: 'boolean' },
          detail: { type: 'string', description: '验证过程描述' }
        }
      }
    },

    reworkSuggestion: { type: 'string', description: '失败时的修复建议' }
  },
  async execute(args) {
    const allPassed = args.results.every(r => r.passed)
    await ctx.requirements.submitAcceptance(args.requirementId, {

  }

设计原则

需求面板的三层流水线不是硬编码的业务逻辑——它是事件驱动的状态机。每一层的流转由事件触发，任务队列派发器通过监听事件串行派发。这意味着任何一层都可以被替换或扩展：加一个"设计评审层"只需注册新事件 + 新状态 + 新队列监听器，不改现有代码。

优化 1：双队列分离（需求队列 ↔ 执行队列）

蓝图把「提出需求」和「执行」压成一条线：submit → queued → 队列 worker 自动派发。这导致需求一旦提出就立即执行，没有沉淀和评审窗口。实际实现拆成两个队列，语义清晰：

// 需求队列：不自动执行，可编辑
const backlog = []      // stage: 'backlog'
// 执行队列：丢入后 FIFO 串行执行
const execQueue = []    // stage: 'queued' → 'executing'

createRequirement(input)  // → backlog（不 pump）
dispatchToExec(id)      // backlog → execQueue → pump()
recallFromExec(id)       // execQueue → backlog（撤回）
收益

需求可先在需求队列里编辑、评审，再决定何时丢到执行队列；执行队列只关心「按什么顺序跑」。

优化 2：执行与验收解耦（待验收池）

蓝图里队列 worker 的 busy 标志要等 accepted/rework 才释放，导致一个需求停在「待验收」时整个执行队列被卡住。实际实现把「执行完成」作为释放点：任务执行完即进入待验收池，立即取下一个执行。

executeTask(req, exec).then(summary => {
  finalizeExecution(id, summary)   // → accepting（待验收池）
  busy = false                    // 立即释放队列
  pump()                            // 取下一个
})
收益

同一时刻只有 1 个任务在「执行」，但可以有 N 个任务堆积在「待验收池」；验收通过/返工完全异步，不再阻塞流水。

优化 3：需求可编辑

蓝图的需求创建后不可改。实际实现新增 edit_requirement 工具 + update RPC，可改标题/描述/优先级/范围/命令/绑定工作目录；配合返工，形成「返工 → 修改 → 重新丢执行」的修正闭环。

优化 4：返工自动重入 + 上限保护

验收不通过（或执行异常）时，需求 reworkCount++ 后自动重入执行队列队尾；连续返工超过 MAX_REWORK=5 则退回需求队列，避免死循环。

优化 5：执行队列拖拽排序 / 置顶 / 撤回

执行队列支持拖拽排序与置顶，让用户在派发前动态调整优先级；撤回把任务退回需求队列。

专用面板主 agent（执行器父级）

任务执行不再挂载在当前会话下，而是由面板专用主 agent 作为所有执行器的父级：

要点实现
创建方式agents.create({ sessionId: 'dsh-task-panel-*', meta: { cwd }, agentOptions, setup }) 懒创建并复用
装配继承在 setup(agentCtx) 中调用 agentPresets.composeFrom(agentCtx, root.ctx)，继承根 agent 的 standing composition（{{model}} 变量、工具、persona 段落全部可用）
模型继承 agentDefaultModel.currentSelection()（provider + model）
独立 cwd面板 agent 拥有独立 session 与工作目录，不在其他项目下执行
兜底创建失败时回退根 agent 作为父级，保证任务仍可执行（诊断见 list_requirements 的【面板agent】行）
踩坑记录

裸 agents.create（无 setup 装配）会导致执行器起不来：{{model}} 无值、工具/提示词段落缺失。正解是 setup 里调 agentPresets.composeFrom(agentCtx, root.ctx)，与 DSH 官方子代理继承父级装配的方式一致。

暂停 / 停止 / 恢复

操作状态流转实现
⏸ 暂停executing → pausedrun.dispose() 中断在途子 agent，产物标记「已暂停」

▶ 恢复paused → queued → executing重入执行队列自动重执行（新增一轮）
